# Unit 14 — Password Attacks

- **Module:** Module 3 — Exploitation (final unit of Module 3)
- **Suggested week:** Week 14
- **Estimated time:** 5 × ~50-min class periods
- **PEN-200 mapping:** Password Attacks

> Passwords are still the front door to most systems — and most break-ins. This unit, the last in Module 3, shows **how passwords are stored** (and why plaintext is a disaster), how attackers attack them **online** (against a live login) and **offline** (against stolen hashes), and the tools they use — **Hydra**, **John the Ripper**, and **Hashcat** — entirely against **authorized lab targets**. As always, every attack is paired with its defense: **long unique passwords, MFA, account lockouts, and strong hashing**. You'll finish with a journal of lab-cracked credentials and a reflection on how to defend them.

## Learning objectives
By the end of this unit, students can:
- **Explain** how passwords are stored — plaintext (bad), **hashing**, and **salting** — and why hashing is one-way.
- **Identify**, at an awareness level, common hash types (**MD5**, **SHA**, **bcrypt**) and which are weak vs. strong.
- **Distinguish** **online** attacks (against a live service) from **offline** attacks (against captured hashes), including their trade-offs.
- **Compare** brute-force vs. **dictionary/wordlist** attacks and explain why wordlists like **rockyou** are so effective.
- **Use** **Hydra** to attack a **lab** login service with a wordlist.
- **Use** **John the Ripper** (and/or **Hashcat**) to crack **sample** hashes offline.
- **Describe** **password spraying** and why it evades simple lockouts.
- **Recommend** defenses — long unique passwords, **MFA**, account **lockout**/rate-limiting, and strong salted hashing (bcrypt) — and explain how each breaks a specific attack.

## Standards alignment
- **NICE Framework:** Knowledge of cryptography and authentication (K0019, K0044), password/credential attacks (K0362); Tasks — assess authentication controls, recommend mitigations (T0176). Work role exposure: Vulnerability Assessment Analyst, Security Control Assessor.
- **CSTA / state CS standards:** 3A-NI-05 (recommend security mitigations), 3B-NI-03 (cryptography concepts), 3A-IC-30 (impacts of computing).
- **Security+ domain(s):** 1.0 (password attacks — spraying, brute force, dictionary), 2.0 (hashing, salting), 3.0/4.0 (MFA, lockout, secure authentication).

## Key vocabulary
| Term | Student-friendly definition |
|------|------------------------------|
| Plaintext password | A password stored as readable text — a disaster if the database leaks. |
| Hash | A one-way scramble of data; the same input always gives the same hash, but you can't reverse it. |
| Hashing | Turning a password into a hash so the real password isn't stored. |
| Salt | Random data added to each password before hashing, so identical passwords get different hashes. |
| MD5 / SHA | Older/general-purpose hash algorithms — fast, which makes them **easier to crack** for passwords. |
| bcrypt | A slow, salted password hash designed to resist cracking — a strong choice. |
| Online attack | Guessing passwords against a **live** login service (e.g., a website or SSH). |
| Offline attack | Cracking **captured hashes** on your own machine, with no contact to the target. |
| Brute force | Trying every possible combination — thorough but slow. |
| Dictionary / wordlist attack | Trying a list of likely passwords — much faster and usually more effective. |
| Wordlist | A file of candidate passwords (e.g., **rockyou.txt**, from a real breach). |
| Hydra | A tool for online attacks against login services. |
| John the Ripper / Hashcat | Tools for offline hash cracking (Hashcat is GPU-accelerated). |
| Password spraying | Trying **one** common password against **many** accounts to dodge lockouts. |
| MFA | Multi-factor authentication — a second factor (code, key, app) beyond the password. |
| Account lockout / rate-limiting | Blocking or slowing logins after too many failed attempts. |

## Materials & prep
- **Authorized TryHackMe** password-attacks room (browser-based, e.g., a Hydra/John lab) **and/or** a local lab login service (a lab VM running SSH/FTP/HTTP with known test creds) on the isolated network. Free.
- **Kali Linux** VM (or AttackBox) with **Hydra**, **John the Ripper**, **Hashcat**, and the **rockyou** wordlist (Kali ships rockyou at `/usr/share/wordlists/rockyou.txt`, often gzipped). Free.
- A handout of **sample hashes** generated by the instructor for offline cracking (MD5/SHA/bcrypt examples) — see prep notes.
- Projector for the hashing/salting diagram and the online-vs-offline comparison.
- Handouts: the password-attack worksheet (in `lab.md`), the lab-journal rubric and report rubric from `instructor/grading-and-rubrics.md`.
- **Instructor prep notes:**
  - Confirm the lab is **fully isolated** (host-only/internal). Any login service used as a Hydra target must be a **lab account on a lab system** — never a real account or real service. See `instructor/lab-setup-guide.md`.
  - **Generate sample hashes yourself** from harmless words that appear in rockyou (e.g., hash `password1`, `summer2024`, `letmein` as MD5/SHA-1, and one bcrypt) so John/Hashcat will actually crack them in class time. Keep a key of which plaintext maps to which hash. Do **not** use real users' passwords.
  - Decompress rockyou if needed: `gunzip /usr/share/wordlists/rockyou.txt.gz`.
  - Pre-create lab login accounts with passwords that exist in a small wordlist so Hydra succeeds quickly. Provide a trimmed wordlist for speed on weak hardware.
  - Pre-test the exact Hydra and John commands and their runtimes on lab machines. Make clear that "real" cracking can take far longer — class examples are intentionally crackable.

## ⚖️ Ethics & legal callout
This is one of the easiest skills to misuse, so the line is bright: you attack **lab accounts on lab systems** and **authorized TryHackMe rooms** — **never** a real account, a classmate's account, a school login, or any service you don't own or have **written permission** to test. Even a single unauthorized login attempt can be a crime under the CFAA and state law. There's a privacy dimension too: the **rockyou** wordlist is real passwords from a real breach — proof that what people choose gets exposed. We study these attacks to **defend** people: to push for MFA, lockouts, strong hashing, and long unique passwords. Cracked credentials from this lab are **lab data only** and never leave the lab.

**Discussion prompt:** A friend forgot their email password and asks you to "just crack it for them — it's their own account." Is that okay? Walk through why even a well-meaning request can cross legal/ethical lines, and what the right answer is (account recovery, not cracking). Where is the authorization boundary?

## Lesson sequence

### Day 1 — How passwords are stored: hashing & salting
- **Warm-up (5–10 min):** "When a website stores your password, what *exactly* is in the database? Should it be the password itself?"
- **Direct instruction (15–20 min):** Plaintext (disaster) → **hashing** (one-way scramble; same input → same hash, can't reverse) → **salting** (random per-password data so identical passwords differ). Awareness of **MD5/SHA** (fast → bad for passwords) vs. **bcrypt** (slow + salted → good). Show a word and its hash on the board.
- **Guided practice (15 min):** Generate a hash of a sample word together; show that the same word always hashes the same, and that one character change totally changes the hash. Define plaintext, hash, salt, MD5/SHA, bcrypt.
- **Independent practice / lab:** In journals, students hash two sample words and record the outputs; write one sentence on why hashing beats plaintext.
- **Closure / exit ticket (5 min):** "Why does salting make a stolen password database harder to crack?"

### Day 2 — Online vs. offline; brute force vs. wordlists
- **Warm-up (5–10 min):** "Would you rather attack a live login or a stolen hash file? Why?"
- **Direct instruction (15–20 min):** **Online** (against a live service — noisy, slow, can trigger lockouts) vs. **offline** (against captured hashes — quiet, fast, limited only by your hardware). Then **brute force** (every combination) vs. **dictionary/wordlist** (likely passwords) — and why wordlists like **rockyou** win because people reuse predictable passwords.
- **Guided practice (15 min):** Estimate, as a class, how the time to crack changes with password length and with "is it in rockyou?" Introduce **password spraying** (one common password across many accounts → dodges lockouts).
- **Independent practice / lab:** **Read the Safety & authorization reminder in `lab.md` aloud.** Begin the lab setup; locate `rockyou.txt`; inspect (don't run yet) the Hydra command.
- **Closure / exit ticket (5 min):** "Give one advantage of an offline attack and one of an online attack."

### Day 3 — Online attack with Hydra (lab login only)
- **Warm-up (5–10 min):** "What does an attacker need to start guessing a login?" (username, a wordlist, the service/port.)
- **Direct instruction (15–20 min):** Introduce **Hydra**: targeting a service (SSH/FTP/HTTP-form), supplying a username and a wordlist, reading results. Re-state: **lab account on a lab system only.** Connect to defense: this is exactly what **lockout/rate-limiting** and **MFA** stop.
- **Guided practice (15 min):** Paced demo: run Hydra against the **lab** login service with a small wordlist; watch it find the password.
- **Independent practice / lab:** Students run Hydra against the **authorized lab service** (or THM room) and capture the found credential in the worksheet.
- **Closure / exit ticket (5 min):** "Name two defenses that directly defeat a Hydra-style online attack, and how."

### Day 4 — Offline cracking with John the Ripper / Hashcat
- **Warm-up (5–10 min):** "You stole a file of hashes. The target has no idea. How do you turn hashes into passwords?"
- **Direct instruction (15–20 min):** **Offline cracking**: feed the **sample hashes** + a wordlist (rockyou) to **John** (and/or **Hashcat**); identify the hash type; read cracked results. Show why **fast hashes (MD5/SHA)** fall quickly while **bcrypt** resists — tying back to Day 1.
- **Guided practice (15 min):** Crack a couple of sample MD5/SHA hashes together with John; observe the speed difference if a bcrypt sample is included.
- **Independent practice / lab:** Students crack the provided **sample hashes** with John (Hashcat optional), record which cracked, which didn't, and why.
- **Closure / exit ticket (5 min):** "Why did the bcrypt sample resist cracking when the MD5 one fell fast?"

### Day 5 — Defenses + document it (ends Module 3)
- **Warm-up (5–10 min):** "After this week, what password advice would you actually give your family?"
- **Direct instruction (10–15 min):** Map each attack to its defense: **long unique passwords / passphrases** (beat wordlists & brute force), **MFA** (a stolen password isn't enough), **lockout/rate-limiting** (kills online guessing & slows spraying), **strong salted hashing — bcrypt** (makes offline cracking impractical). Reinforce **password managers** and not reusing passwords. Review the journal/report rubric (`instructor/grading-and-rubrics.md`).
- **Guided practice / independent lab:** Students finalize their **journal of cracked creds (lab)** and write a **password-defense reflection** matching each lab attack to a concrete defense.
- **Closure / exit ticket (5 min):** Submit the reflection; one-sentence takeaway: "the single best password defense for most people is ___ because ___."
- **Assessment:** Unit quiz (`assessment.md`) at end of Day 5; this closes Module 3.

## Differentiation
- **Support:** Provide a trimmed wordlist and pre-created lab account so Hydra succeeds fast. Give copy/paste Hydra and John commands with each flag labeled. Supply a "hash type → strong/weak" reference card. Pair students. Use the browser-based TryHackMe room for weak hardware. Provide sentence frames for the defense reflection ("The ___ attack works by ___. The defense ___ stops it because ___.").
- **Extension:** Use **Hashcat** with a rule set or a mask attack and explain it; crack a salted hash and explain how the salt is handled; build a tiny custom wordlist and discuss targeted guessing; research a real breach where weak hashing (or plaintext) made things worse and summarize the lesson; or estimate crack-time for different password lengths and present the math.

## Homework / independent work
- Finish the Hydra lab and the John cracking exercise if not done in class.
- Complete the **journal of cracked creds (lab)** with commands, results, and screenshots.
- Write the **password-defense reflection** (½–1 page): match each attack you performed to a specific defense.
- Personal action: audit your own password habits (length, reuse, MFA on) — write 3 changes you'll make. (No sharing of real passwords.)

## Assessment
- **Formative:** Daily exit tickets; the salting/hash check; instructor walk-around confirming each student can run *and* explain Hydra and John; the attack→defense mapping.
- **Summative:** Unit quiz + journal of cracked creds + password-defense reflection — see `assessment.md`.

## Instructor notes & common pitfalls
- **Bright line on targets.** Hydra and John are trivially misusable. Restate every lab: **lab accounts on lab systems and authorized rooms only — never a real account, a classmate's, or a school login.** Cracked creds are lab data and never leave the lab.
- **Make the labs actually crack in class time.** Generate sample hashes from words that exist in rockyou and pre-set lab passwords accordingly; otherwise students wait forever and learn the wrong lesson ("cracking doesn't work"). Be explicit that real cracking can take days/years — your examples are intentionally easy.
- **Tie speed to algorithm.** The MD5-falls-fast / bcrypt-resists contrast is the key teaching moment and the bridge to the bcrypt defense. Include one bcrypt sample on purpose.
- rockyou is sometimes gzipped — pre-decompress on lab machines or students will be stuck at the first command.
- Watch the "it's their own account" trap (the discussion prompt): even well-intentioned cracking of someone else's account is unauthorized. The answer is account recovery, not cracking.
- **Always pair attack with defense.** End every day on the mitigation. The reflection (attack → defense) is the summative anchor and closes Module 3. Attacks are always paired with defenses.
